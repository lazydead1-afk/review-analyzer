# Architecture

The pipeline separates deterministic preprocessing, probabilistic extraction, and deterministic consumption:

```text
reviews → clean → deduplicate → LLM extraction → aggregate → UI / evaluation
```

Cleaning removes only obvious empty, junk, and spam inputs. Cross-channel deduplication selects canonical reviews before inference. Groq then classifies each remaining review into a constrained sentiment, issue taxonomy, and severity. Strict runtime validation rejects malformed or incomplete batches, and trusted review IDs are attached locally by input order rather than generated by the model. Aggregation, dashboard filtering, and evaluation are deterministic.

This boundary makes the system reproducible and auditable: every excluded review has a reason, duplicate relationships are inspectable, invalid LLM output cannot enter the checkpoint, and the UI reads a stable processed artifact instead of making model calls on page load.

# Biggest decisions and trade-offs

## 1. Deterministic preprocessing before the LLM

Cleaning and cross-channel deduplication do not require an expensive or non-deterministic model. Running them first reduces cost and keeps preprocessing easy to test and explain. Deduplication is deliberately precision-first, using exact normalization and a high near-match threshold. The trade-off is that it can miss semantic duplicates that use substantially different wording.

## 2. Constrained global issue taxonomy and structured output

A shared taxonomy prevents equivalent problems from fragmenting into arbitrary labels and makes aggregation and evaluation straightforward. Groq uses strict JSON Schema output, followed by runtime validation of result count, sentiment, issue names, severity, booleans, and structure. The trade-off is reduced nuance: ambiguous feedback may be forced into `other`, or a fixed taxonomy may omit a distinction useful to a specific product.

## 3. Static processed artifact and checkpointed batch analysis

`processed-reviews.json` makes the dashboard fast, inspectable, and usable without an API key. Atomic checkpoints make a long analysis run resumable. A batch size of five, strict response validation, bounded rate-limit retries, and limited validation retries were practical reliability choices. The trade-off is that this is a batch snapshot rather than a live production ingestion system.

# Evaluation and failure analysis

The evaluation uses 20 manually labeled reviews selected to cover sentiment classes, multiple issues, severity levels, multilingual text, sarcasm, typos, and common issue categories. One labeled spam case is intentionally filtered before inference, leaving 19 predictions.

- Sentiment accuracy: **94.7% (18/19)**
- Issue F1: **91.3%**
- Severity accuracy: **76.2% (16/21)**

Severity calibration is the weakest dimension. Five matched issues had the wrong severity, with several medium or low cases over-escalated. In multi-issue feedback, one food-quality issue was missed. A French account-access case was classified as `other`, producing one missed and one extra issue, and a billing complaint gained an extra refund issue. The single sentiment error interpreted sarcastic praise plus a crash as mixed rather than negative. These are observed disagreements, not claims about hidden model reasoning.

# With another week

- Build a larger, stratified, independently reviewed labeled set.
- Calibrate severity with clearer boundary examples and a refined rubric.
- Add embeddings or semantic similarity to improve near-duplicate recall.
- Improve observability around provider errors, retries, latency, and token usage.
- Refine the taxonomy using measured confusion patterns.

# Deliberately cut

Database storage, authentication, deployment, multi-tenancy, live ingestion, embeddings/vector infrastructure, and elaborate charts were intentionally excluded. They would add operational surface area without demonstrating the core review-analysis workflow within a 4–6 hour take-home scope.
